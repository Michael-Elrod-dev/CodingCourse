The big idea

How do we make code
represent a thing?

Variables, loops, and methods all work on loose, separate values. Today we learn to bundle the data and the actions that go with it into one unit — an object — built from a class.

By the end you'll have built an Enemy that knows its own health and how to take damage. First, watch how the pieces fit.

1 — The old way

Loose, disconnected pieces

To remember one enemy we need two variables. For two enemies, four — and nothing ties a name to its own health.

goblinName
goblinHealth
skeletonName
skeletonHealth
Debug.Log(goblinName + " has " + skeletonHealth + " HP");
→ "Goblin has 12 HP"  ✗   one enemy's name, another's health — C# never complains

Four values in a row. The computer has no idea which ones belong together.

2 — The idea

Group them into one unit — an object

A real thing has stuff it is and stuff it does. A class lets code define a brand-new kind of thing the same way.

🚗

Car

one object — what it has and what it does, together
Fields — what it has
make
model
color
Methods — what it does
Start()
Stop()
Move()

Fields = the data it carries. Methods = the things it can do.

4 — See it live

Each object is its own thing

Two players from one Player blueprint. We score Ana twice — and Bo never moves.

Ana

score: 0
untouched ✓
ana.AddPoints(70); Ana scores 70! Total: 70

Same blueprint, separate objects. Touching Ana does nothing to Bo.

The link back to Session 3

Fewer things to pass

Last week your methods needed everything handed in. When the data lives on the object, the method already has it.

Last week
TakeDamage(name, health, amount)
you passed everything in — three things
This week
goblin.TakeDamage(amount)
just one — the goblin already knows its own name & health

The data and the actions on it finally live together.
